# 정비 사례 원고 작성

**입력** — 정비 폴더(`G:\내 드라이브\1.정비작업사진외\<번호. 차종 번호4자리 정비내역>\`)의 `원고.txt` + `원2` 사진.
**출력** — 채팅에 네이버 세트·Astro 세트·자체 점검. 저장소에는 `_draft.json`(작업 파일)과 변환된 이미지만 남는다.
**끝나면 멈춘다.** 승인 후 `publish-case` 가 이어받는다.

## 내용 규칙은 여기 없다

**문체·금지어·필드 규칙의 단일 소스는 `docs/원고작성/작성지침.md` 다.** 이 스킬은 절차만 담는다. 규칙을 여기에 옮겨 적으면 두 벌이 되어 반드시 어긋난다.

작업 전에 읽는다:

| 문서 | 역할 |
|---|---|
| `docs/원고작성/작성지침.md` | 무엇을 어떻게 쓸지 (314줄, 절대 규칙 포함) |
| `docs/원고작성/문체예시/` | 어투·문장 리듬 — **네이버 세트에만** 적용한다 |
| `docs/원고작성/문체예시/README.md` | 예시 안의 금지어 위치. 예시와 지침이 충돌하면 **지침이 우선** |
| `src/content.config.ts` | Astro 프론트매터 필드·타입 |
| `CLAUDE.md` | 불변 사실 (브랜드·지역·인증·A/S) |

문체예시는 **네이버 글** 예시다. Astro 본문은 기존 사례(`src/content/cases/*/index.mdx`) 문체를 따른다 — 예시를 Astro 본문에 적용하면 이미 발행된 글들과 결이 어긋난다.

## 1. 입력 확인

`원고.txt` 를 읽어 아래를 뽑는다. **필수 항목이 없으면 그것만 묻고 멈춘다** — 지어내지 않는다.

| 항목 | 필수 | 비고 |
|---|---|---|
| 차종 | ✔ | 브랜드 + 모델 + 연식 |
| 주행거리 | | 숫자만. **없으면 `mileage_km` 필드를 생략**한다. 추정 금지 |
| 입고사유 | ✔ | 고객이 말한 증상 또는 예약 목적 |
| 점검 | ✔ | 진단 방법과 확인된 상태 |
| 정비 | ✔ | 실제 수행한 작업 |
| 결과 | ✔ | 정비 후 상태·출고 상황·대기 부품 |
| VIN | | 제원 조회용. **글에는 절대 넣지 않는다** |

`원고.txt` 가 CP949 로 저장돼 있을 수 있다. 깨져 보이면 인코딩을 바꿔 다시 읽는다.

**슬러그**는 `publish-case` 의 명명 규칙(`<브랜드영문>-<차종>-<증상한글>`)으로 만들고 기존 사례와의 중복을 확인한다. 사용자가 준 값이 있으면 그것을 쓴다.

## 2. 이미지 변환 — 잠정 번호

```
node .claude/skills/publish-case/prepare-images.mjs <slug> --from="<정비폴더>\원2"
```

판독하려면 이미지를 읽어야 하는데 원본은 장당 5~18MB다. 먼저 변환해 작은 webp 를 읽는다.
**번호는 잠정값이다** — 배치는 원고가 나온 뒤에 정해지므로, 최종 번호는 `publish-case` 가 `--renumber` 로 매긴다.

`t_` 가 1개가 아니면 스크립트가 중단한다. `x_` 는 제외, 나머지는 괄호 순번 순이다.

## 3. 판독

`images/` 를 **한 장도 빠짐없이** Read 로 열어 아래를 판정한다. 파일명·순서로 추측하지 않는다.

| 항목 | 내용 |
|---|---|
| 피사체 | 차량 전체 / 엔진룸 / 하부 / 부품 단품 / 계기판 / 도면 / 소모품 |
| 부위 | 식별 가능한 범위까지 |
| 상태 | 탈거 전·후 / 신품·구품 / 파손 노출 여부 |
| 공정 단계 | 입고 · 점검 · 원인 확인 · 부품 준비 · 작업 · 완료 · 출고 |

- **원고에 근거가 없는 부위명을 지어내지 않는다.**
- 시각적으로 구분되지 않으면 `uncertain` 으로 두고 사유를 적는다. 추측으로 확정하지 않는다.
- 도면·부품 카탈로그는 실물 사진과 구분한다.

**중단 조건은 하나뿐이다** — 고장 부위 근접샷이 한 장도 없으면 멈추고 알린다. 사진에 찍힌 차량번호는 중단 사유가 아니다.

## 4. 원고 생성

작성지침에 따라 **① 네이버 세트 → ② Astro 세트** 순으로 만든다. 중간에서 멈추지 않는다.

사진을 보고 쓴다는 점이 젬과 다르다 — 판독 결과를 본문 서술에 반영해, 글과 사진이 처음부터 맞물리게 한다.

## 5. `_draft.json` 저장

`src/content/cases/<slug>/_draft.json` 에 아래를 쓴다. `.gitignore` 대상이라 커밋되지 않는다.
승인 후 `publish-case` 가 이 파일을 읽으므로 **사진을 두 번 판독하지 않는다.**

```json
{
  "slug": "...", "brand": "포르쉐", "model": "포르쉐 카이엔S 디젤",
  "sourceFolder": "G:\\...\\원2",
  "overlay": { "line1": "PORSCHE CAYENNE S", "line2": "엔진오일교환 · 연료필터 카트리지 교환" },
  "naver": { "focusKeyphrase": "", "title": "", "seoTitle": "", "slug": "",
             "metaDescription": "", "tags": [], "body": "", "faq": [] },
  "astro": { "frontmatter": {}, "body": "" },
  "readings": [{ "n": 1, "source": "...", "subject": "", "part": "", "state": "",
                 "stage": "", "uncertain": false, "reason": "" }],
  "evidence": [{ "claim": "DPF 차압 이상 확인", "source": "원고.txt 점검" }]
}
```

**오버레이 문구** — 1행은 `src/data/brands.json` 의 `en` + 모델명을 대문자로. 2행은 `<슬러그 증상부> · <정비 첫 항목>`. 띠 폭을 넘으면 `overlay.mjs` 가 글자를 줄이거나 항목 하나만 남긴다(자르지 않는다).

## 6. 자체 점검

```
node .claude/skills/publish-case/check-manuscript.mjs <slug>
```

세는 검사는 스크립트가 한다 — 글자수·description·FAQ·태그·금지어·차량번호·진단기 표기·지역·부품 출처. **FAIL 이 있으면 고쳐서 다시 돌린다.** 사람이 세게 하지 않는다.

### 근거 대조표는 스킬이 만든다

기계가 못 잡는 위험은 **원고에 없는 사실을 지어내는 것**이다. 본문의 기술적 주장마다 출처를 `evidence` 에 적고, 표로 함께 낸다.

```
[근거 대조]
  "DPF 차압 이상 확인"          ← 원고.txt 점검
  "EGR 쿨러 누유"               ← 원고.txt 점검
  "냉각수온 정상 범위 확인"      ⚠ 출처 없음
  "부품 입고 대기"              ← 원고.txt 결과
```

출처는 `원고.txt <항목>` 또는 `사진 NN` 이다. 둘 다 아니면 `source: null` 로 두고 `⚠` 로 낸다 —
**지어낸 문장은 정의상 출처가 없으므로 반드시 여기 걸린다.** 사용자가 전문을 정독하는 대신 `⚠` 만 훑을 수 있게 하는 것이 이 표의 목적이다.

## 7. 출력하고 멈춘다

```
① 네이버 세트 전문
② Astro 세트 (프론트매터 + 본문)
③ 자체 점검 + 근거 대조표
```

**여기서 반드시 멈춘다. 승인 없이 `publish-case` 로 넘어가지 않는다.**
원고가 틀리면 배치·캡션·alt 가 전부 헛일이 되므로, 되돌리는 비용이 가장 큰 지점이 여기다.

- 사용자가 특정 부분만 지시하면 **그 부분만** 고친다. 전체를 다시 쓰지 않는다.
- 한쪽만 고치라는 지시가 없으면 두 세트 모두에 반영한다.
- 수정 후 자체 점검을 다시 돌려 결과를 함께 낸다.

승인되면 `publish-case` 로 넘어간다 — 배치 → `--renumber` → 오버레이 → 「리」·「홈」 → MDX → 빌드 → 커밋. 그 뒤로는 멈추지 않고 결과만 보고한다.
